## 八张变六张可以说明什么

若 nvidia-smi 仅列出当前六张设备，可确认此次查询可见设备数与配置数量不一致。要指出缺少哪两张，需要正常设备身份清单、设备错误信息或其他能识别缺失设备的证据；仅凭 expected_count=8 与 actual_count=6 不足以推断身份，更不能直接判断两张硬件损坏。

跨次查询不应只按 GPU 索引判断缺失身份。NVIDIA 官方说明驱动枚举顺序不保证重启后一致，建议使用 UUID 或 PCI Bus ID 作为一致性标识，见 [nvidia-smi 官方文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。历史清单仍需与同一主机、对应硬件配置及时点匹配；映射到物理槽位还需要相应映射资料。

缺失身份的集合比较由确定性代码完成。多种证据之间的解释、按适用 SOP 选择下一步检查、形成有来源的复核说明，可以作为 LLM 的候选职责，尚未证明该部分比普通工具更省时。

## 候选方案比较

| 方案 | 可提供的作用 | 限制 |
| --- | --- | --- |
| 当前记录与 SOP 问答原型 | 说明已知差异，查找文档方法 | 没有覆盖现场的额外取证步骤，尚无员工提效证据。 |
| 一键异常复核工具 | 复用原始输出，必要时执行固定的只读诊断脚本，比较正常与异常设备清单 | 固定流程可以由普通脚本实现，不能把这部分收益全部归因于 LLM。 |
| 在复核工具上加入 Agent | 根据当前证据选择受控检查工具、结合文档解释、指出缺失依据 | 需要比固定脚本方案多测模型等待、核对与返工；增加诊断工具和调整任务预算均未实施。 |

建议以 GPU 数量异常作为一个试点，先定义可复核的结果，再同时比较原有人工操作、固定复核工具与 Agent。此处是待验证方向，不是已批准或已实现的新功能设计。

## 首次价值实验应记录什么

- 输入：同一主机适用的正常设备清单、异常时的实际命令输出或原始日志、对应配置基线与检查 SOP。缺少输入时如实说明，不能用虚构的正常清单解释真实故障。
- 任务终点：正确区分数量不符、可确认的缺失设备身份、尚未证实的根因，并给出有依据的下一步复核事项。若身份依据不足，正确指出不足也算符合任务要求。
- 对照：现有前端加人工 SSH、固定诊断脚本、带工具的 Agent。比较同样正确结果的人工总用时、人工操作次数、模型等待、核对返工与误判情况。
- 判断：Agent 是否在固定工具已有能力上继续节省时间；没有收益时保留简单工具方案，不宣称 LLM 提效。没有真实员工对照时，模拟实验应明确标注适用范围。
