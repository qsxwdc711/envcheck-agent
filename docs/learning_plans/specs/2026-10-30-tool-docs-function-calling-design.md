# 三工具文档问答的 Function Calling 设计与验收

日期：2026-10-30；更新：2026-11-01。状态：本地原生 Function Calling、RAG、FastAPI 最小业务闭环完成。新入口通过十三项进程内模拟检查，并取得学习者提供的一条真实 HTTP 200 + sufficient 跨资料回答；验证范围见阶段记录，不包含整体准确率、员工提效或生产部署。

## 目标与当前依据

用户只提交自然语言问题，由模型决定检索哪一类工具资料。沿用 getinfo、nic_link_check、aidoc_download 三个资料范围，以及现有 Embedding、Qdrant 工具过滤和资料不足规则。

当前 POST /tools/ask 由用户提供 question 与 tool_name，程序固定执行检索。前期 [tool_call_demo.py](../../../tool_call_demo.py) 已实现工具调用循环、assistant/tool 消息拼接、工具数量与任务时间限制；[app/tools.py](../../../app/tools.py) 已有 JSON 参数解析、Pydantic 校验和统一工具结果结构。新业务复用这些模式，检索目标使用三工具文档集合。

## 两种组织方式

| 方式 | 优点 | 代价 | 本步选择 |
| --- | --- | --- | --- |
| 一个 search_tool_docs 工具，tool_name 是三个合法值之一 | 直接复用现有 ToolRagRequest 与 search_tool_chunks，检索实现集中 | 需要明确函数名和资料分类参数的区别 | 推荐作为第一步 |
| 三个独立检索工具，分别绑定三个资料范围 | 各工具职责直观 | 工具定义与分发数量增加，底层仍复用同一检索函数 | 留作后续比较 |

## 推荐工具契约

函数名为 search_tool_docs。它检索工具的使用资料；模型选择的 tool_name 是资料范围。

输入参数：

- question：非空自然语言检索问题。
- tool_name：getinfo、nic_link_check、aidoc_download 之一。

输出使用已有的 ok、data、error 结构：检索成功时 data 为文档片段列表，片段保留 chunk_id、tool_name、source、section、source_type、content；空命中为 ok=true、data=[]。参数无效时在调用 Embedding 前返回 INVALID_ARGUMENTS。

该工具负责向量化与查询数据库。最终回答由获得工具结果后的文本模型生成，并沿用 RagAnswer 的 answer、evidence_status、citations 三个字段。

## 执行流程

1. 用户提交自然语言问题，首个文本模型请求提供 search_tool_docs 的定义。
2. 模型返回调用请求及参数；Python 从工具白名单中分发，解析并严格校验参数，拒绝额外字段与不合法类型。
3. 执行异步 Embedding，并通过 asyncio.to_thread 调用现有 search_tool_chunks，以 tool_name 过滤；新工具路径当前显式取四个片段。
4. 将原始 assistant 工具请求与对应 tool 消息依次写回对话，tool_call_id 必须匹配。
5. 再次请求文本模型，基于工具返回的数据生成最终 JSON。
6. 校验 RagAnswer 结构；引用 ID 只能来自本次成功工具结果。sufficient 需要文档引用，资料缺失时说明缺口。

2026-11-01 候选数量实验：固定同一 RoCE 查询向量，前三条为 004、002、006，含别名说明的 003 排第四。学习者已在 search_tool_docs 调用 search_tool_chunks 时显式传 limit=4，底层默认值仍为 3。真实回放补齐 003 并正确说明别名，现场配置不足保持 insufficient；getinfo Word 指导与 aidoc 端口问题也完成真实回归。四题核心行为通过，模板措辞有一项建议，不据此声明所有问题改善或整体稳定性指标。

正常的一次检索路径包含两次文本模型请求、一次 Embedding 请求与一次本地检索。相比当前固定 RAG 路径，多出一次模型选择资料范围的文本请求；实际等待时间由后续回放记录。

问题无法判断资料范围时允许先澄清，最终使用 insufficient、空引用。可从需求推断工具时应调用检索，例如“把采集结果生成 Word 报告”对应 getinfo；不要求用户先知道工具名。

## 有界执行与失败边界

沿用前期演示的初始上限：每轮最多一个工具请求，整个任务最多两次工具执行、三次文本模型请求；最后一次模型请求禁止继续调用工具，总任务预算初始为 90 秒，单次 SDK 配置沿用现有客户端。该预算为学习阶段初值，需通过真实回放检查。

工具名采用固定白名单。参数校验、工具结果与模型回答是三个不同环节；解析 JSON 成功不代表参数有效，工具执行成功不代表资料足够，结构校验通过不代表业务结论正确。

空检索返回成功的空列表，生成端说明资料不足。SDK/任务超时与工具服务失败记录为运行失败，保留已有调用轨迹。当前业务仍提供使用指导；服务器登录、安装、交付脚本执行不在这个检索工具的职责中。

## 实现分步

app/usage_tools.py 承载检索封装、声明及严格参数校验；app/usage_agent.py 的公开 run_usage_agent 负责共享预算，内部循环负责至多两次工具/三次文本请求和累计引用；命令行仅调用公开入口。三类资料范围选择、Top-4 四题及实际循环的七种模拟检查均有记录，原别名说明遗漏已通过候选诊断和生成回归修订。

命令行跨工具真实日志显示 getinfo → nic_link_check → 最终回答，第三次设 none，引用覆盖两轮。新 POST /agent/ask 只接收 question，复用同一业务入口，实际十三项 HTTP 模拟检查通过，随后取得学习者提供的真实 HTTP 200 回答；本条正确区分 getinfo、RoCE 与 IB 场景，原样响应见 [阶段验收记录](../../tool-usage-agent-evidence.md)。现有 /tools/ask 保留固定 RAG 对照，旧巡检演示和六题固定用例保留历史记录；它们不等于新接口的批量评测。

## 验收方向

- 三个典型业务问题能选择对应资料范围，并在收到工具结果后回答。
- 需求不明确时先澄清，资料不足时不把示例当作现场配置。
- 不合法参数在 Embedding 前拦截，工具结果与 tool_call_id 正确匹配。
- 模型请求和工具执行不超过上限；超时与错误可区分，引用只来自本次资料。
- 离线先用模拟依赖核对分发和消息流程；真实模型调用由学习者执行。
