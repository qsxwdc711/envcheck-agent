# 交付运维工具知识助手：项目介绍与简历草稿

整理日期：2026-10-30；更新：2026-11-01。项目类型：个人项目，基于实习中的交付运维业务延伸开发。当前为本地 RAG 与原生 Function Calling 原型，面向内部交付运维团队的工具使用场景。

## 简历版本（STAR）

**项目名称：交付运维工具知识助手｜个人项目（实习业务延伸）**

**技术栈：Python、FastAPI、asyncio、Pydantic、原生 Function Calling、Qdrant、火山方舟模型 API**

**项目介绍：** 针对交付运维人员使用 getinfo、nic_link_check、aidoc_download 时难以快速确认前置文件、命令参数及操作步骤的问题，开发工具知识助手，实现自然语言提问、资料自动检索及带引用的使用指导。

**个人职责与成果：**

- **Agent 接口与编排：** 基于 FastAPI 与 asyncio 封装统一执行器，通过原生 Function Calling 让模型选择资料范围，由程序校验参数并分轮执行检索，打通仅提交问题的 HTTP 问答及跨工具资料综合回答。
- **RAG 与输出约束：** 完成三类工具资料清洗、章节/步骤切分、Embedding 及 Qdrant 入库，保留工具名、来源和片段 ID；结合工具维度过滤、Pydantic 与跨轮引用集合校验，提供结构化答案、来源追溯及资料不足提示。
- **检索质量优化：** 针对 RoCE 参数别名说明遗漏，核对 CLI 并修订片段，按原 UUID 增量更新；固定查询向量比较 Top-3/4/7，定位必要片段排第四并调整检索数量，回放后正确解释别名，现场配置缺失时仍返回资料不足。
- **执行边界与验证：** 设置每任务最多两次工具执行、三次文本请求及 90 秒共享预算，统一 HTTP 输入校验与异常响应；建立固定 RAG 用例并保存回放记录，通过正常、资料不足、超时等模拟分支检查及真实 HTTP 联调验证处理链路。

## 项目口述参考

我基于实习期间接触的交付运维工具，做了一个工具使用问答的个人项目。使用者需要了解输入文件、命令参数和结果查看方式，原型的目标是让这些使用说明更容易查找，并给出资料来源。

用户只提交自然语言问题，模型先生成 search_tool_docs 调用和资料范围。Python 严格校验参数，把检索问题向量化，带 tool_name 过滤条件查询 Qdrant，最多取四条片段，再把原工具请求与工具结果回填对话。需要另一类资料时可继续检索，最终检查 RagAnswer 与跨轮引用集合。一次任务最多两次工具执行、三次文本请求，并共用 90 秒预算；资料不足时说明缺口。

评测时，我发现回答没有讲清两个参数名的关系，还把可选输出参数说得像必填。核对 CLI 定义后，我在资料准备流程补齐说明，对修改片段重新生成向量并更新原点，再回放通用方法和现场配置不足两个问题。新回答明确了别名和可选性，也保留了缺少现场参数时的资料不足提示。

后来另一条查询仍漏掉了已修订的参数片段。我固定同一个查询向量比较 Top-3、Top-4、Top-7，发现必要片段排第四，于是在新工具路径试取四条，回放确认模型取得并正确引用这条证据，再验证现场条件不足时仍不猜配置。这个过程分别检查了资料内容、检索覆盖和最终生成。

## 2026-11-01 Function Calling 进展补充

当前新增的 usage_agent_demo.py 已实现命令行场景下的资料范围选择、检索工具执行、assistant/tool 消息回填、第二轮最终回答与 RagAnswer/引用范围校验。用户只描述 Word 报告需求时，模型选择 getinfo 并生成有引用的使用指导；RoCE 需求正确选择 nic_link_check；镜像制作端口问题选择 aidoc_download 并正确回答 240404 对应 10022，引用 aidoc-usage-004。当前 FastAPI 的 /tools/ask 仍接收 question 与 tool_name，尚未接入此新演示。

RoCE 本次返回 004、002、006，遗漏已修订的 003，导致最终回答未解释当前版本中两个 leaf 列表参数互为别名；只读核对确认修订已入库。因此当前可说明三类资料选择已有真实证据，不将其描述为三类全部用法验收或答案始终稳定。接下来改善检索证据覆盖、统一失败/澄清返回、总预算与有界调用流程，再接新接口。
